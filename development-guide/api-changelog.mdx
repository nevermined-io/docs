Clients pin an API version per API key (editable in the dashboard) or per request
via the `Nevermined-Version` header; the platform reshapes requests and responses so

## 1.70

- **Router: a payment the merchant answered with an error (HTTP 4xx/5xx on the paid call, x402 exact or MPP-tempo charge) reads deliveryStatus "not_delivered" instead of "pending" until reconciliation decides whether the merchant charged; the delegation cap reserve is held exactly as before. GET /api/v1/router/payments (JSON and CSV) and GET /api/v1/purchases carry the new value; `GET /api/v1/router/delegations/{id}` adds a not_delivered key to spentMicrosByDeliveryStatus. Clients pinned below 1.70 read "pending" for those payments and the not_delivered spend folded into pending.** (`response`)

  - `GET /api/v1/purchases`

## 1.43

_Changes relative to `1.34`:_

- **BREAKING (shipped as a MINOR — see note): POST /organizations/:orgId/billing/upgrade no longer applies the tier inline. It now returns upgraded:false with requiresPayment:true and a clientSecret for a standalone PaymentIntent; only the payment_intent.succeeded webhook grants the tier. A client resolved below 1.43 CANNOT render the PaymentElement, so the handler REFUSES it up front with BCK.BILLING.0031 (an error, before any Stripe change) rather than returning a half-usable success — so this gate never actually reshapes a success response for an old client (it only ever sees 1.43+ responses); it is retained to register the 1.43 version boundary and as defence-in-depth. Released as 1.43 rather than 2.0.0 deliberately: the API version is the monorepo-wide MAJOR.MINOR, and a major bump would force every client on every endpoint to re-evaluate its pin for one endpoint whose old behaviour was itself a money bug (it granted paid tiers without payment). The break is now explicit (a 400 that names the required version), not a silent shape change, which is why a minor + the 0031 refusal is the deliberate choice.** (`response`)
  - `POST /api/v1/organizations/:orgId/billing/upgrade`
